# 사업·개발 공통 작업방법론 (2026-10-29)

## 핵심 원칙
사업을 시작할 때 곧바로 코딩하거나 자동화하지 않는다. 성공 조건을 브레인스토밍하고 여러 구조를 비교한 뒤 전체 목표·성과 기준을 정한다. 전문 영역별 팀과 충돌을 조정하는 총괄팀을 만들고, 수동 파일럿에서 병목을 찾아 검증 가능한 자동화로 전환한다.

사업 문제 정의 → 다각도 브레인스토밍 → 구조 대안 비교 → 성공 기준 → 업무 분해·우선순위 → 담당·지원·총괄팀 → 수동 실험 → 독립 검증 → 충돌·실패 분석 → 자동 수정·후속 과제 배정 → 실제 사용자 검증 → 회고.

## 한글쉽지 자동화에서 배운 실패와 개선
1. 초창기에는 지시받은 작업을 마치고 종료하여 다음 시간까지 대기했다. 시간표에 따른 반복 실행은 연속 개발이 아니다.
2. 10회 컨트롤러 실험 #40787546688은 개발 지시 1회, WAIT 9회였다. WAIT를 생산 성과로 세지 않는다.
3. 6팀 병렬 실행을 도입했으나 충돌·실패·취소가 발생했다. 격리 브랜치, 단일 실행 통로, 파일 소유권과 독립 검증을 추가했다.
4. 160개 백로그에 번호·담당팀·검증 증거·신호등을 연결했다. GREEN(단계별 검증), YELLOW(대기), RED(실패)를 구분하고 코드 검증과 사업 최종 완료를 혼동하지 않는다.
5. AI가 위험한 코드 변경을 제출하면 총괄팀이 반려하고 정확한 수정 지시를 재전달한다. 15팀 충돌 검사 약화 사례는 회귀 CI #40792293256으로 검사했다.
6. 새 작업 없는 팀은 불필요하게 호출하지 않는다. 실패 재시도에는 한도를 두고 독립 검증 중인 작업을 중복 개발하지 않는다.
7. 자동화의 완성은 '배정→실제 작업→독립 검증→실패 수정 또는 통과→다음 과제'의 폐회로다. 다만 24시간 무중단 작업과 전체 160개 완성은 아직 입증되지 않았다.

## 모든 프로젝트에 고정 적용할 규칙
- 브레인스토밍 단계에서 목표·고객·위험·실패 조건을 먼저 적고 대안 구조 2~3개를 비교한다.
- 과제별 담당팀, 선행 조건, 충돌 가능성, 인수 기준, 테스트와 증거를 문서화한다.
- 총괄 판정은 실행팀과 분리한다. 테스트를 약화하는 변경은 차단한다.
- 실패하면 원인·재현·수정 범위·통과 조건을 명시해 재작업을 배정한다.
- 운영 배포·실결제·개인정보·운영 DB 변경은 별도 승인한다.
- 보고에는 실제 변경 SHA, 테스트, 신규 검증 과제, 최종 완료 과제, 실패·대기 원인, 다음 조치를 기록한다.

## 가동률과 생산성 측정
실질 가동률 = 중복 시간을 제거한 유효 개발·검증 작업시간 / 관측 기간. 별도로 대기시간, 차단시간, 신규 독립 검증 과제/시간, 실패 복구시간, 충돌·취소 건수, 최종 완료 과제 수를 측정한다. '3~5분 작업 후 한 시간 대기'는 초기 운영 경험을 설명한 예시이며 실측 평균으로 확정하지 않는다. 최근 실행 시간이 짧아졌다고 생산성이 같은 비율로 늘었다고 주장하지 않는다.

## 2026-10-29 기준선과 재사용 방식
160개 중 코드 검증 5개, 최종 완료 0개(당시 보고 기준). 실제 테스트 홈페이지 검증 미완료. 다음 사업에도 이 문서를 별도 방법론으로 복제한다. 중요한 실험마다 '가설/변경/증거/관찰/실패·성공/배운 점/다음 적용 규칙'을 추가한다.
